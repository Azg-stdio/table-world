# M3 — Multiplayer

**Goal:** authoritative host; clients send intents and receive state; players receive the host's assets on join.
**Done when:** friends on different networks join by Relay code (and later through Steam) and play any table together, seeing each other move things live; a client without local assets receives everything.
**Done when (full M3):** 3 players (2 virtual + 1 build) with 200 ms simulated latency and no desync; two machines connect through Steam.
**Status:** in progress (T3.1–T3.4 done; next: T3.6 playtest). **Depends on:** M2 (War playable).

## Assumptions recorded during implementation

| Task | Assumption |
|---|---|
| T3.2 | Protocol in `core/Net` (ADR 0002): the host orders commands; clients predict their own and rebuild when the host orders differently; remote commands apply in place when nothing is pending. Physics: the host reports poses for every object; a client only for objects its player touched in the last 4 s. Undo/redo are local-only (disabled while networked). Seats: host plays the first seat, each joining client the next free one. Join by address in the HUD (Host / Join, default 127.0.0.1:7777) until Relay join codes (T3.3). The done check used two real processes (Editor + built player) instead of Multiplayer Play Mode virtual players, which can only be enabled from the MPPM window. |
| T3.3 | The Unity project was already linked to a UGS project ("Table World"); anonymous sign-in and Relay needed no dashboard step. Package `com.unity.services.multiplayer` 2.4.1 (sessions API): a private session with `.WithRelayNetwork()` and our own `INetworkHandler` (`RelayLobby.Handler`), so the session only allocates Relay and `NetworkTableSession` still starts NGO and registers its message handler before any message can arrive. HUD: **Host LAN**, **Host online** (shows the code in the address field and copies it to the clipboard), **Join** (takes an address or a code). Seats and colours come from the table's seats (host first seat, joiners the next free one); roles are host and player; spectators are not implemented (no seat left: the joiner gets none). Two processes on one machine need different auth profiles (`-tw-profile`), or they are the same anonymous player. |
| G1–G3 presence | `core/Net/Presence.cs`: frames carry the pointer and held poses with a sequence number; the newest wins and a player silent for 1.5 s fades out. Sent up to 15/s when something changed and every 0.5 s otherwise, unreliable sequenced (reliable if a frame is large); the host relays and overwrites the seat with the one it assigned. A carried object is kinematic on other screens and glides (rate 18/s, interpolation off); its pose is reported only by the holder (the host skips objects a client held in the last 4 s). Presence never changes the table. |
| T3.6 prep (Miguel's solo test, 2026-10-23) | Three findings from playing UNO alone over LAN (Editor + build): the joiner's camera started on the host's side; there was no way to play other than the button list; hands lay flat on the table with their faces visible to everyone. Now: the start view faces from the local seat's hand zone (`TableCamera.FaceFrom`); `core/Engine/Gestures.cs` turns "drag a card out of your hand" and "drag from a pile" into the matching legal action (refusing, with the reason, what the rules own but do not allow now); hand cards stand facing their owner, spread evenly, and show backs (and no name) to everyone else. Hiding is view only for now: every client receives the whole table (a protocol-level fix is a gap to track). |
| T3.6 prep | Players open games from the HUD (**Games**): the build ships the repo's `games/*.json` in `StreamingAssets/Games` (copied by `ShipSampleGames` after each Windows build) and lists the player's own folder `<persistentDataPath>/Games` (a `.json`, or a folder with `table.json` and images). Only the host can open a game while connected. Rules actions are seat-checked online; free-play table commands are not (anyone may move anything, as in TTS), and every client receives the whole table, so hidden hands are hidden by the view, not by the protocol. Company name is still Unity's default, so data lives under `LocalLow/DefaultCompany/Table World`. `unity command build run` writes `runInBackground: 0` into ProjectSettings on every build (restore the file afterwards); `NetworkTableSession` sets `Application.runInBackground` itself, so networked players never pause. |
| T3.4 | Protocol in `core/Net/AssetSync.cs`. The manifest (`id`, `hash`, `size` of every non-builtin image the host has a file for) travels inside each snapshot, so join, resync and a table reload all refresh it. Transfer is receiver-driven: 16 KB chunks, at most 4 in flight per client. Commands share the reliable sequenced pipe, so everything in flight sits ahead of the next command: with 16 chunks a command could wait over a second behind images; with 4 the Relay throughput barely changed (45 s → 51 s for 10.7 MB) and commands stay near 200 ms. The transport's reliable window (64 packets) caps throughput at about 90 KB per round trip; base64 adds a third. Keep shared images compressed (JPEG for photos and boards). Cache: one file per SHA-256 under `%LOCALAPPDATA%/TableWorld/cache/assets/` (no eviction yet). Objects show their plain colour until the image arrives, then repaint. Limits: 32 MB per asset. Images only; models after M4. When the host loads another table while hosting, every client receives the new snapshot and a new command order. Asset paths must stay inside the package (`invalid_path`), because the host sends those files to every player. The MCP bridge now sends the game file's folder as the package root. |
